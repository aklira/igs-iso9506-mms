# S3 — `igsmms-server`, the demonstration server and the bench device

## Prompt

Run task S3 of `IMPLEMENTATION.md`: a demo server with variables from a TOML file, usable as the bench
device under test. Done when it is documented and a run against the bench peer is recorded here.

## Summary

- **Code**: `crates/igs-iso9506-mms/src/bin/igsmms-server.rs` (clap, serde, toml; the file is checked as
  the model checks it), and the library change of D-027 in `crates/igs-iso9506-mms-link/src/association.rs`.
- **Bench**: the service `device` (`172.31.102.30`, port 10103 on the host) and `device-capture` in
  `bench/docker-compose.yml`, the file `bench/device/demo.toml`, and `bench/tests/test_s3_device.py`.
- **Documentation**: `docs/igsmms-server.md` (usage, file format, behaviour, bench), `bench/README.md`.
- **Decisions**: D-027 (the MMS annex application context accepted by the responder), D-028 (the binary, the
  format, the static build for the bench).
- **Gaps found**: G13 (application context 1.0.9506.2.3, fixed by D-027), G14 (the journal query of the
  reference client refused, recorded), and G2 (direction) is now tested for the reference client.
- **Gate**: `porte=1` (fmt, clippy, doc, test, msrv 1.85, deny, codegen --check).

## Found on the way

The first run of the reference client against the device failed at association: the server answered
`rejected-permanent` with diagnostic `application-context-name-not-supported`. The reference client proposes
`1.0.9506.2.3`, and the server accepted only `1.0.9506.2.5` (G13). The decoding of the refusal in the capture
showed it (`tshark -V`, the ACSE section, frame 15). D-027 accepts both names. The test of the link layer
checks the refusal of another name and the echo of the accepted one.

The second run failed on the variable directory (`mms_utility -t`): the reference client then asks for the
journals of the domain, the device refuses (G14), and the client exits with status 82. The test records that
output rather than hiding the exit status.

## Run on the host (`igsmms-server` and `igsmms-client`)

The server runs as the static binary, on 127.0.0.1:10103, with `bench/device/demo.toml`:

```
$ igsmms-server --listen 127.0.0.1:10103 --config bench/device/demo.toml
igsmms-server: listening on 127.0.0.1:10103
```

Commands of `igsmms-client` (this repository's client, `-s 127.0.0.1:10103 --timeout 10`):

```
$ igsmms-client identify
vendor: igs
model: igsmms demo
revision: 0.1
[exit 0]

$ igsmms-client names --class domain
demo
[exit 0]

$ igsmms-client names --domain demo
label
status
temperature
[exit 0]

$ igsmms-client names --class named-variable-list --domain demo
snapshot
[exit 0]

$ igsmms-client read temperature --domain demo
FloatingPoint(FloatingPoint([8, 65, 172, 0, 0]))
[exit 0]

$ igsmms-client read status --domain demo
true
[exit 0]

$ igsmms-client attributes temperature --domain demo
deletable: false
address: None
type: FloatingPoint(TypeDescriptionFloatingPoint { format_width: Unsigned8(32), exponent_width: Unsigned8(8) })
[exit 0]

$ igsmms-client write speed 7 --kind int
written
[exit 0]
```

The float is shown as its octets (`8, 65, 172, 0, 0`, the single precision 21.5): the CLI prints the codec's
value, it does not decode floats yet.

## Run against the bench (reference client, `mms_utility`)

The device container runs the same binary (`bench/docker-compose.yml`, service `device`), and the reference
client connects to `172.31.102.30`:

```
$ mms_utility -h 172.31.102.30 -i
MMS connected.

Server identity:
----------------
  vendor:	igs
  model:	igsmms demo
  revision:	0.1
[exit 0]

$ mms_utility -h 172.31.102.30 -d
MMS connected.

Domains present on server:
--------------------------
demo
[exit 0]

$ mms_utility -h 172.31.102.30 -t demo
MMS connected.

MMS domain variables for domain demo
  label
  status
  temperature

Failed to read domain journals (error=82)
[exit 82]

$ mms_utility -h 172.31.102.30 -a demo -r temperature
MMS connected.
Read SUCCESS
21.500000
[exit 0]

$ mms_utility -h 172.31.102.30 -a demo -r status
MMS connected.
Read SUCCESS
true
[exit 0]

$ mms_utility -h 172.31.102.30 -r label -a demo
MMS connected.
Read SUCCESS
igs
[exit 0]
```

`bench/tests/test_s3_device.py` runs these commands, captures the device's network namespace, and checks
the capture: the services 1, 2 and 4 are on the wire in both directions, the initiate exchange is there, and
no frame is malformed (the release artefact G6 is filtered). The test passed (`1 passed`).

## Help

```
MMS server over TCP (RFC 1006). It serves the VMD described by the configuration file: the identity, the domains, the named variables and the named variable lists. Each connection is one association. The server runs until it is stopped (Ctrl-C). The format of the file is in docs/igsmms-server.md.

Usage: igsmms-server [OPTIONS]

Options:
  -l, --listen <ADDRESS>
          The address to listen on, as host:port. RFC 1006 uses TCP port 102
          
          [default: 127.0.0.1:102]

  -c, --config <FILE>
          The configuration file: the VMD to serve. Without it, the server serves an empty VMD

      --max-associations <COUNT>
          The associations held at once; a connection beyond them is closed
          
          [default: 64]

      --nesting <LEVEL>
          The deepest nesting of data structures the server proposes (ISO 9506-1 §8.2.1.1.4). The server negotiates the nesting with the client, which may propose less
          
          [default: 2]

  -h, --help
          Print help (see a summary with '-h')

  -V, --version
          Print version
```
