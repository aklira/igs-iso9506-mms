# T2 — Client API

## Prompt

Run task T2 of `IMPLEMENTATION.md`: a `Client` with connect and reconnect policy, the services in
scope, an event stream of unconfirmed reports and connection state, bounded channels with documented
back-pressure. Done when the integration tests against the loopback pass for each service.

## Summary

- **Code**: `crates/igs-iso9506-mms/src/`.
  - `client.rs`: `Client` (connect, request, the typed methods of the eight services in scope, close),
    `ClientConfig`, `Reconnect`, `ConnectionState`, `Event`, `Events`.
  - `connector.rs`: `Connector`, the source of the byte streams, with `TcpConnector`.
  - `actor.rs`: the background task: one owner of the connection, the association and the requests;
    the queue at the limit; the reconnection with backoff; the close with its abort fallback.
  - `error.rs`: the client's errors (refused, service error, rejected, timeout, connection lost, closed,
    unexpected).
- **Link layer, extended**: `Requests::can_request`, `Requests::is_open`, and
  `Event::RejectIndication` for an indicated request the client does not serve.
- **Decisions**: D-021 (API, queue, events, timeouts, reconnection, close).
- **Tests**: `tests/client.rs`, 16 tests against a loopback server built from the link layers. Each
  service in scope has its test, and the connection behaviours are covered.
- **Gap G1**: the close is decided here, with the abort after the request timeout (`docs/capabilities.md`).
- **Gate**: `porte=1`.
- **Found while testing**: the loopback server processed its actions in reverse order, so its own
  release was wrong; the test server now processes them first in, first out. The library was right.
